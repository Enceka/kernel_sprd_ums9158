# E5 原厂镜像与设备取证（`stock-img/` + `kernel_probe/`）— 2026-09-12

本轮把 `stock-img/`（原厂分区镜像）和 `kernel_probe/`（设备取证）重新从设备上采回 ——
工作区里这两份已经不在了，而 `artifacts_e5/*.md` 大量引用它们。采集全部走**宿主 macOS 的
adb**（`adb shell su`，不用 `adb root`），每个落盘文件都做了设备端 / 宿主端 sha256 双向比对。

## 1. 设备与产出

| 项 | 值 |
|---|---|
| 设备 | `TS30520241202952`，`ums9158_1h10`（E5），活动槽位 `_a` |
| 运行内核 | `5.15.119-android13-8-00018-ga78ea39db117-ab10710420`（2023-08-24 构建，**原厂**） |
| `stock-img/` | 19 个镜像，490 MB，清单 `SHA256SUMS` |
| `kernel_probe/` | 13 个文件，23 MB，清单 `SHA256SUMS` |

采法（可复用）：

```sh
adb exec-out 'su -c "dd if=/dev/block/by-name/boot_a bs=1M 2>/dev/null"' > stock-img/boot_a.img
adb shell    'su -c "sha256sum /dev/block/by-name/boot_a"'   # 与本地 shasum -a 256 比对
```

`vendor_dlkm` **不是物理分区**（`/dev/block/by-name/` 里没有），它在 `super` 内，走
`/dev/block/mapper/vendor_dlkm_a`（dm-6）。两个采集上的坑：

- `kallsyms` 默认没有地址（`kernel.kptr_restrict=2`，全 0）。要看地址需临时
  `echo 0 > /proc/sys/kernel/kptr_restrict`，**取完已恢复为 2**。`=2` 时符号名与模块归属
  仍然有效（如 `sprd_glb_mm_pw_on_cfg … [sprd_camsys_pw_domain]`），只是缺地址。
- `adb pull` 的目标不要经 macOS `/tmp` 再 `cp` 进工作区：OrbStack 共享挂载不允许写 macOS
  扩展属性，`cp` 会以非 0 退出（数据已写入，但会中断后续步骤）。直接 `adb pull … kernel_probe/`。

## 2. 事实清单（与既有文档不一致的标 ⚠）

| 事实 | 证据 |
|---|---|
| ⚠ `boot_a` 的 ramdisk **不为 0**，且是 Magisk 的 | 头部 v4：`kernel_size=0x2C96A00`、`ramdisk_size=0x58188`（360,840 B，起始 0x2C98000，LZ4），`overlay.d` / `.backup` 字面量落在 ramdisk 区。README 原本写"stock 的 ramdisk_size=0"：当前设备刷的是**原厂内核 + Magisk ramdisk** |
| ⚠ `dtb_a` / `dtb_b` 全为 0（空分区） | 8 MB 分区非零字节数 = 0，全盘无 FDT magic → DT 只能来自 `dtbo`，正向印证 README 的说法 |
| `dtbo_a` 内确有 FDT | 偏移 `0x60` 处一个 `totalsize=118667` 的 FDT，含 `sprd,ums9621`、`lcd_st7365p_mipi_hdp`×5、`tlsc6x`×9；live FDT 285,820 B 与之并非逐字节相同（是合并结果） |
| `boot` 不含 DT（README 说法成立） | `boot_a/b` 内 FDT magic = 0；补充：`vendor_boot_a/b` 各含 **1** 个 FDT magic（README 未提），`init_boot_a/b` = 0 |
| Magisk 的实际落点是 `init_boot` | `init_boot_a`：`kernel_size=0`、`ramdisk_size=1,907,183`（LZ4），含 `overlay.d`×3 / `.backup`×2 |
| A/B 两槽仅 `init_boot` 不同 | `boot_a==boot_b`、`vendor_boot_a==vendor_boot_b`、`dtb` / `dtbo` / `vbmeta*` / `avbmeta*` 两槽全同；`init_boot_a`≠`init_boot_b`（首差在偏移 `0xc`，1,907,183 vs 1,832,230） |
| AVB footer 分布 | `boot`/`init_boot`/`dtbo`/`vendor_boot` 分别 1/1/1/4 个 `AVBf`；`vendor_dlkm_a` 没有（逻辑分区，AVB 走 `vbmeta_vendor`）。footer 字段是**大端** |
| `pstore` 空、ylog 已轮转 | `/sys/fs/pstore/` 空；`/blackbox/ylog` 只剩 3.1 MB（会话 28/29/30），09-11 文档引用的 174/24/26 等已不在 |
| 设备时钟未同步 | `date` = 2026-07-02 22:45（uptime 979 s）→ 采集文件的 mtime 是设备 RTC，不代表真实时间 |

## 3. 可直接用的一个点

`repack_boot_e5.sh` 的 `BASE` 默认指向 `/home/hema/Workspace/e5/magisk_patched-30700_hNDcW.img`

```sh
BASE=stock-img/boot_a.img ./repack_boot_e5.sh
```

## 4. 为什么这两个目录不入库

合计 513 MB，保持未跟踪。内核版本号的 `-dirty` 判定出自 `scripts/setlocalversion`：

```sh
git --no-optional-locks status -uno --porcelain 2>/dev/null || git diff-index --name-only HEAD
```

`-uno`（`--untracked-files=no`）意味着**未跟踪文件不参与判定**，所以这两个目录不会造成
dirty build；只有已跟踪文件的改动（例如改过 `build_e5.sh`）才会。
